# 本机自学习调参（SELFTUNE）：设计说明

用户要求：在**用户设备上**、**不引入大库**的前提下，加入针对"可变因素"的自学习算法
（自然进化策略 NES 一类），让软件适配不同人的使用习惯，暗中持续优化。
用户判断这属于大方向改动，版本步长 **+300**（当前 1.9.142，落地时递增到相应版本）。

本文是设计说明（先定清楚"调什么、看什么信号、怎么判定变好、怎么保证不会变坏"），
实现与验证随后按此进行。**未验证的东西不写进 CHANGELOG 当成功**。

## 一、原则（写死，避免跑偏）

1. **纯 Kotlin、零新依赖**：算法本体目标在数百行以内，不使用任何 ML 运行时；
   不引入 ONNX / TensorFlow / DJL 之类。
2. **全部本地**：不采集、不上传任何个人数据；学习结果只写在本机配置里。
3. **只在自身可观测的范围内调参**：不做"猜用户喜好"的黑箱；每个被调参数都能被
   人读懂、被日志解释。
4. **不许变坏**：任何参数都有硬边界；有"守擂者/挑战者"机制，挑战者必须赢过守擂者才生效；
   出现失败率上升立刻回退到默认。
5. **可关闭**：提供开关（环境变量或设置项），关闭后行为与现在完全一致。
6. **先量后改**：算法每一步决策都要能在日志里看到依据（窗口、适应度、θ 变化、是否采纳）。

## 二、调什么（可变因素）

第一阶段（桌面端，已验证存在的瓶颈与候选）：

| 参数 | 现取值 | 范围 | 说明 |
| --- | --- | --- | --- |
| `prefetchDepth` | 6 | 2 至 12 | 预取提前量。翻页快的人受益，慢慢看的人浪费带宽 |
| `prefetchConcurrency` | 1 | 1 至 3 | 预取并发。串行保证近处优先；并发提高吞吐但会挤占带宽 |
| `cacheBudgetMB` | 256 | 64 至 512 | 图片缓存上限。内存紧的设备应调小 |
| `retryBackoffMs` | 现有默认 | 200 至 3000 | 下载失败后的退避，网络差的人需要更宽容 |

第二阶段（需要更多观测才能安全纳入）：解码目标尺寸（与已测得的"解码只占 86ms、
下载占 1078ms"相关，若调小无收益则不纳入）、横向模式预渲染页数、章节预取开关。

**不纳入**：任何影响正确性的参数（反切片公式、页码映射、缓存淘汰语义）。

## 三、看什么信号（全部来自本机既有日志/计数）

| 信号 | 来源 | 用途 |
| --- | --- | --- |
| 单页呈现耗时 | 反切片总耗时、下载耗时、"预取第 N 页"日志 | 适应度的延迟项 |
| 缓存命中 | 分界后"反切片是否紧跟下载行"的配对 | 适应度的命中率项 |
| 每页下载字节 | `[反切片] 下载 …B` | 适应度的带宽项 |
| 失败与取消次数 | 下载异常、取消守卫、加载失败行 | 安全项（越界即回退） |
| 停留时长、翻页方向、翻页间隔 | 阅读页新增的轻量打点（仅计数与耗时） | **习惯项**：区分"快翻"与"慢读" |

习惯项的判据（明确、可解释）：以本次会话的**中位停留时长**为分界，
快翻用户（中位停留小于约 1 秒）加权延迟项，慢读用户加权带宽项。
这就是"适配不同使用习惯"的具体含义，而不是玄学。

## 四、怎么判定变好（适应度）

```
cost = wL * 归一化单页呈现耗时中位数
     + wB * 归一化每页下载字节
     + wM * 未命中率
     + wF * 失败/取消率
```

`wL、wB、wM` 由习惯项决定（快翻加大 wL，慢读加大 wB），`wF` 固定为惩罚项且权重最高。
所有项都按"当前会话内可比的量"做归一化，避免不同网络环境下不可比。

## 五、算法（NES，具体形式）

1. 参数先归一化到 [0,1]：`x = (p - lo) / (hi - lo)`；搜索分布为**对角高斯** `N(θ, σ²I)`，
   σ 初值 0.15（归一化空间），整体不超过 0.3。
2. **在线窗口**：每 K 次翻页（例如 K = 20，或会话结束时）为一个评估窗口。
   一个窗口内**只用一个参数向量**，窗口边界的日志统计即为该向量的适应度。
3. **对偶采样 + 排序适应度整形**：每代抽 λ = 6 个候选（3 对 `θ ± σ ε`），
   按适应度排序得到整形权重 `u_k`（无梯度、抗噪）。
4. **更新**：`θ ← θ + (η / (λ σ)) Σ u_k ε_k`，`σ` 按成功比例按缓慢规则收缩/扩张
   （成功定义：本代最好者优于守擂者）。η 取小值，保证一次最多移动范围的约 20%。
5. **守擂者/挑战者（安全阀）**：始终保留 incumbent（当前生效的 θ）。挑战者必须在
   同一窗口类型（同习惯档）下**明显优于**守擂者才被采纳，否则丢弃并把参数写回守擂者。
   这等价于 (1+1)-ES 的 1/5 成功规则，用来兜住在线噪声。
6. **失败即回退**：窗口内失败/取消率超过阈值，立刻写回默认值并暂停学习一个冷却期。

## 六、状态存储

- 位置：应用数据目录下的 `selftune.json`（含 schemaVersion、θ、σ、incumbent、窗口计数、
  冷启动标记、上次更新时间）。
- 冷启动值 = **当前手工调好的默认值**（预取 6、并发 1、缓存 256MB），
  所以刚装上或升级后的行为与现在完全一致，不会因为算法未收敛而变差。
- 解析失败或版本不认识：**丢弃并回到默认值**（绝不带着半截状态运行）。

## 七、怎么验证（分三层，前两层我自己就能做完）

1. **算法本体单元测试**：合成带噪声的二次目标，固定随机种子，断言在若干代内收敛到
   最优附近（给出容差），并且相同种子结果可复现。
2. **离线回放（关键）**：用**已记录的真实日志**做仿真器 —— 已有的 2450 条下载样本
   （含字节数与耗时）与翻页时间戳，可估计"给定 `prefetchDepth = d`、`concurrency = c` 时，
   用户翻到第 N 页时它是否已预取完成"，从而算出期望延迟与期望带宽。
   然后让算法在这段真实轨迹上跑，验证两件事：
   - 快翻轨迹上它把 `prefetchDepth` 调大；
   - 慢读轨迹上它把 `prefetchDepth` 调小（省带宽）。
   若做不到这两点，说明算法或适应度设计有问题，**不许上线**。
3. **真机验证**：日志里输出每个窗口的 θ、适应度、是否采纳；跑一次真实会话后，
   由日志判断它是否按预期调整（并检查有没有抖动、有没有越过安全边界）。

## 八、分阶段

| 阶段 | 内容 | 可交付的验证 |
| --- | --- | --- |
| P1 | 算法本体 + 单测 + 离线回放；先只调 `prefetchDepth` 与 `prefetchConcurrency`，日志模式（只记录建议值，不生效） | 单测通过；回放显示快翻/慢读两种轨迹下建议方向正确 |
| P2 | 打开生效（带守擂者/挑战者与硬边界），加入 `cacheBudgetMB`、失败回退、开关 | 真机日志显示采纳过程与回退都按预期 |
| P3 | 习惯项细化（停留时长、翻页方向、会话长度），扩展到 Android 端 | 与 2.0.0 一起，单独出 CHANGELOG 说明 |

**P1 只记录不生效**，是为了先拿到"它的建议是否合理"的证据，再让它动真实行为 ——
符合"先量后改"，也避免一上来就悄悄改变用户体验却无法解释。

## 九、明确不做

- 不引入任何 ML 运行时或大依赖；不采集上传数据；不做无法解释的黑箱调参；
- 不改动任何影响正确性的逻辑（反切片公式、页码、缓存语义）；
- 不在窗口中途改变参数（避免同一页行为不一致）；
- 不把"学习结果"当成已验证效果 —— 效果仍然要用日志指标说话。

## 十、离线回放实测（2026-10-04，判据通过）

**数据来源，必须分清**：
- **真实**：`shared/src/test/resources/selftune-trace.csv` 是从真机日志里抽出的 **177 条反切片下载样本**
  （字节数, 下载毫秒），取自同一连续时段（字节中位数 898KB、下载中位数 836ms、范围 221 到 4170ms）；
- **构造**：停留时长。日志里几乎没有停留记录（只有 16 行键盘翻页），所以构造了四种场景
  （150ms 狂点、400ms、1000ms、4000ms 慢读）。**结论里必须带上这条限制。**
- **模型**：页面最多提前 d 页开始下载，可用提前时间 = min(d, 当前页序号) × 每页停留；
  需要时间 = 下载毫秒 / 并发数；够则命中（延迟约 0），不够则延迟 = 缺口 + 完整下载时间；
  结尾处被预取但未看到的 d 页字节按页均摊计入浪费。模型刻意保持简单、可解释。

**深度扫描（中位延迟 / 150 页中的命中数）**：

| 停留 | d=2 | d=3 | d=4 | d=6 | d=9 | d=12 |
| --- | --- | --- | --- | --- | --- | --- |
| 150ms | 1896ms / 5 | 1709ms / 28 | 1535ms / 46 | 1231ms / 72 | 790ms / 113 | 565ms / 128 |
| 400ms | 1341ms / 60 | 911ms / 100 | 643ms / 120 | 383ms / 134 | 207ms / 141 | 147ms / 143 |
| 1000ms | 453ms / 131 | 180ms / 142 | 49ms / 147 | 20ms / 148 | 20ms / 148 | 20ms / 148 |
| 4000ms | 12ms / 149 | 12ms / 149 | 12ms / 149 | 12ms / 149 | 12ms / 149 | 12ms / 149 |

浪费（页均摊）随深度近似线性：d=2 约 15KB/页，d=12 约 79KB/页。

**回放结果（判据：狂点场景选出的深度 >= 慢读场景）**：
- 狂点（150ms/页）：深度 **7**、并发 2、缓存 374MB、退避 572ms；
- 慢读（4000ms/页）：深度 **3**、并发 1、缓存 89MB、退避 1680ms；
- 断言 `7 >= 3` 通过。

**这张表说明了两件事**：
1. **方向正确**：翻页越快，延迟项越重要，算法把深度调大；翻得慢时延迟项已饱和（d=2 就命中 149/150），
   再加深度只是多下载，于是算法把深度收小。
2. **常见阅读速度下最优深度并不大**：1000ms/页时 d=6 已到 20ms 延迟、命中 148/150，再深没有收益。
   这也解释了此前"预取 v2 提前 6 页仍未见中位数下降"的实测 —— 瓶颈不在深度，而在单页下载本身。

**限制（不得省略）**：停留为构造数据、模型为简化模型、173 条样本只代表一段网络状况；
所以本回放只能证明**方向**与**量级**，不能当作真机收益的证明。真机收益仍以 `.work/verify.sh` 的实测为准。
