## 与 Android 端一致的若干约定（实现时照抄，别自创）

- **无章节作品**：作品 id 自身就是可读单元（单话同人本），详情页要能直接开读
- **章节列表倒序**：最新一话在最上面
- **列表过滤统一在数据层**：页面只显示 `PagedList.hidden`，不要各页自己过滤
- **屏蔽命中要在页面顶部提示**"有内容被屏蔽规则挡掉"，不能静默少几条
- **阅读进度**记录到章节粒度（`ReadProgressStore`），详情页据此显示"继续阅读"

## 收藏页的缺口清单（1.9.x，实测于本轮）

用户的判断"分类往后直到追更全是残缺的"在收藏页体现得最集中。逐项核对如下：

| 项 | Android 端 | 桌面端现状 | 卡在哪 |
| --- | --- | --- | --- |
| 排序档位 | `favorites(order = ...)`，`DEFAULT_FAVORITE_ORDER = "mr"` | **`order` 参数从未使用** | 需要 Android 端的档位定义（我这次没抓到，下一轮先读全再改） |
| 文件夹切换 | `favorites(folderId = ...)` + `state.folders` | **完全没做** | **共享层没有"文件夹列表"接口** —— 只有 `favorites()` 与 `favoriteTags()`，Android 的 `state.folders` 来源我尚未定位 |
| 取消收藏 | 列表内可移除 | **没做** | 接口现成（`toggleFavorite(aid)`，详情页已在用），缺的是列表项的额外操作位 |
| 追更的位置 | **不是独立页面**，是收藏页里的标签 | 桌面端做成了**独立页面** | 结构不一致，需要合并成标签 |
| 新建/改名/删文件夹、移动作品 | 有（`editFavoriteFolder`） | 没做 | 依赖文件夹接口 |

结论：收藏页要真正补齐，**先要解决"文件夹接口在哪"**这一个前置问题；
在此之前能安全做的是排序档位与取消收藏（两者接口都现成）。

顺带记一条方法论：这一页我如果先动手加文件夹 UI，一定会卡在"没有数据来源"上；
先把前置依赖查清再改，比边写边撞省时间。这也是"先量后改"最实际的用法。

## 历史页的"删除一条"：未做，已回退（连败四次，留待整文件重写）

目标：历史页每条加「删除」按钮（Android 端有，走 `deleteHistory(comicId)`，该接口**共享层早已存在**）。
结果：连续四次失败，最终回退、不留半成品。四次原因各不相同：

| 次 | 失败原因 | 我的误判 |
| --- | --- | --- |
| 1 | `FavoritesScreen.kt` 缺 `import TextButton` | 以为是 items 块作用域问题 |
| 2 | `ListPages.kt` 同样缺 import | 我 grep 过 import 却没核对输出 |
| 3 | **设计错**：`scope` 只存在于 AccountListPage 内部，而我把 lambda 定义在外层函数 | 我固化了"那个报错=缺 import"的结论 |
| 4 | **perl 分隔符冲突**：替换文本含 `//`，而 `s///` 用 `/` 作分隔 | 没先检查替换文本里有没有分隔符 |

根源是同一个：**在不了解结构、不熟悉工具语义的情况下反复打补丁**。

据此加一条硬规则：**同一个改动失败两次，就停止打补丁，改为整文件重写。**
依据是本会话的实测经验 —— `RemoteImage.kt`、`UpdateCheck.kt`、`WallpaperLayer` 都是
整文件重写后一次成功，而多次打补丁的成功率明显更低。

接口已确认现成，下次只需：给 `AccountListPage` 加 `itemDelete: (suspend (ListItem) -> Unit)?`，
由页面**内部**启动协程（因为 scope 在里面），成功后移除并减总数，失败只记日志、列表不变。

## 布局类问题的实测经验（1.9.x，含一条重要的反面证据）

**真病因**：顶层状态行写成 `Row(Modifier.fillMaxSize())` ✗ —— 它占满整个高度，
下面的列表拿不到空间，于是"数据到了、计数对、一个封面都不画"。
用户验证过的修复：把那三页（历史/追更/随机）整文件重写，布局约定写进注释。

**反面证据（很重要）**：我一度以为"`Column` 里的列表必须用 `weight(1f)`" ✗，
但全库扫描发现**很多页面用的是 `fillMaxSize`，其中收藏页是用户亲口验证通过的** ✓。
所以：

> `Column` 里的列表用 `fillMaxSize` **并不一定出问题**——两种写法都能正常工作。

结论：**不要按推论做批量改动** ✗。我在容器里看不到界面，批量改可能把本来好的页面改坏，
而且只能等用户发现。正确做法是：**按用户报告的"哪一页坏了"去查那一页** ✓，
扫描脚本只作辅助定位，不做全库替换。

## 一条流程病根：无条件覆盖包

我此前的构建命令是 `gradle ... | grep BUILD; cp -a ...` —— **无条件复制** ✗，
于是编译失败时 `/root/jmnext-new` 仍是旧镜像，我却让用户去测，白跑几趟。
用户的批评原话：「你编译了吗让我跑来了」。

已改为受保护脚本：只有日志出现 `BUILD SUCCESSFUL` 才覆盖包，失败则包不动并打印错误。
**待补**：偶发失败自动重试一次（出现过一次"构建偶发失败、紧接着重跑即成功"，
保护机制因此把一次**本可以成功**的更新憋住了）。

## 随机页的"按收藏偏好排序"实现方案（1.9.x，接口已读全）

Android 端做法（`ui/screens/random/RandomListScreen.kt`）：

1. 取**本地缓存的**收藏标签统计 `FavoriteTags.cached()`；只有缓存过期才
   `refresh(repo)`（`DEFAULT_MAX_WORKS = 60`、`DEFAULT_MAX_PARALLEL = 3`）——
   即**不是每次随机都扫收藏**，这点很关键，否则每次点"换一批"都要几十个请求。
2. 对这一批作品逐个取标签：`repo.album(id).tags.toSet()`。
3. `RandomRanking.rank(items, tagsOf, favoriteTags, isBlocked)`。

**签名上的关键细节**（读源码确认，不是猜的）：
```kotlin
fun rank(
    items: List<ListItem>,
    tagsOf: (ListItem) -> Set<String>?,     // ← 同步！不能在里面发请求
    favoriteTags: Map<String, Int>,
    isBlocked: (Set<String>) -> Boolean,
): List<ListItem>
```
`tagsOf` 是**同步 lambda**，所以顺序必须是：**先并发取完这一批的标签存进 Map** →
再把 `{ id -> map[id] }` 传给 rank。若偷懒在 `tagsOf` 里发请求，会阻塞且并发失控。

**桌面端实现计划**：
- 做成**开关**（默认关）：开启才付"每批 N 次详情请求"的代价，关闭时就是现在的随机。
- 取标签时设**并发上限**（照 Android 的 3，或 4），避免把图床/接口打爆。
- 用 `FavoriteTags` 的本地缓存 + 过期才刷新，沿用 Android 的判断。
- 未命中标签的作品 `score = 0`，排序时沉底（`rank` 已如此处理）。
- 代价如实写进界面提示：开启后每批会多 N 次请求、首次可能较慢。

## WebP 转码开销：从日志量出的实测数据（1.9.x）

日志里没有带毫秒的图片行（早期格式有，现在的格式只记字节数），但**转码前后的字节数**记得很全，
因此先量"放大倍数"这一项：

| 项 | 数值 |
| --- | --- |
| 成功转码次数（用户实际运行期间） | 173 |
| PNG/WebP 体积比的中位数 | **8.21 倍** |
| 最大 | **12.66 倍** |
| 反切片解码异常次数 | 1 |

一个例子：`Skiko 转码为 PNG 成功 12300866B（原 1480126B）` —— 1.4MB 的 WebP 解出 12.3MB 的 PNG。

**但要如实说清这个数字的性质**：转码是**内存中的**（Skiko 解出像素后再编码成 PNG 字节，
再解码回 ImageBitmap），PNG 字节是临时对象、不落盘、不长期持有；长期持有的是最终 Bitmap。
所以真实代价是**两次解码 + 一次 PNG 编码的 CPU 时间**，以及一个临时的十几 MB 缓冲，
**不是**"每页多占十几 MB 内存"（这一点容易被体积比误导，写下来避免以后自己搞错）。

**下一步（未做）**：目前日志没有转码耗时的毫秒数，所以我**不能**判断 8.21 倍的体积放大
是否对应可感知的加载延迟。要先在转码处加计时日志（前后各取一次时间），下次用户运行后再量，
再决定是否改成 Skiko 直读像素（那条路有颜色错乱风险，必须留 PNG 兜底）。
在拿到耗时之前不动这条路径 —— 没有数据就改，正是这个项目里反复出错的原因。

## 更正：上面「瓶颈是反切片」的结论是错的

上一节写"耗时的大头在反切片"，**这个归因不成立**。读代码后发现：

```kotlin
val t0 = System.currentTimeMillis()          // 计时起点在函数开头
val bytes = download(url, "反切片")           // 下载
... ImageIO.read / Skiko 转码 ...             // 解码
src.getRGB(0, 0, w, h, pixels, 0, w)          // 取出全部像素（2116x3037 就是 640 万点）
ImageUnscramble.unscramble(pixels, w, h, ...) // 还原：只有 System.arraycopy，按 band 整块搬
out.setRGB(0, 0, w, h, fixed, 0, w)           // 回填全部像素
out.toComposeImageBitmap()                    // 转成 Skia 位图
Log.line("反切片成功 ... ${now - t0}ms")      // 这行测的是**上面六段的合计**
```

两点事实：
1. **反切片算法本身已是最优** —— 只有 `System.arraycopy`，没有任何逐像素循环，不该动；
2. 那 2715 ms 是**六段合计**：下载、解码、取像素、还原、回填、转位图，其中"取像素"与"回填"
   各要搬 640 万个 int（约 25MB），加上 `toComposeImageBitmap` 的转换，都是可疑项。

**教训**：我拿日志**标签**当成了测量范围（标签叫"反切片成功"，我就以为它只测反切片）。
以后读测量的第一步是**确认计时区间的起止**，而不是看日志写了什么词。

**这轮已做**：把六段拆开计时，输出一行明细
（下载 / 解码 / 取像素 / 还原 / 回填 / 转位图，各多少毫秒）；
并保证 `runCatching` 块内最后一个表达式仍是位图（否则那段代码的返回值会变味）。
**下一步**：等用户跑一次，读出六段各占多少，再决定动哪一段并写清代价；
若大头在"取像素/回填"，可改用 `BufferedImage` 的 `DataBuffer` int 数组省掉两次全量拷贝。

## 本地基准：像素取/回填不是主因（同尺寸实测）

等不到用户运行明细，就自己量 —— 写了一个不依赖界面的 Java 基准（容器内 JDK 直接跑），
尺寸取用户日志里那张图的真实尺寸 2116x3037（642 万像素、约 24MB 的 int 数组）：

| 阶段 | 实测 |
| --- | --- |
| `setRGB`（回填全部像素） | 45.3 ms |
| `getRGB`（取出全部像素） | 54.4 ms |
| `System.arraycopy` 25MB（反切片那种整块拷贝） | 8.9 ms |
| 取 `DataBuffer` 引用 | 0.1 ms |

**结论：像素取/回填合计约 110 ms，占那 2715 ms 的 4%** —— 所以"改用 DataBuffer 省两次拷贝"
即使做对了也只省 100 ms 左右，**不是主要矛盾**。

**由日志时间戳反推出的真实大头**（同一张图）：

```
18.237  Skiko 转码为 PNG 成功 11882004B（原 1444718B）     ← PNG 编码 + 中间产物 12MB
19.184  反切片成功 2116x3037 1444718B 3282ms                ← 这中间 947 ms 是：
                                                              ImageIO 解码 12MB PNG
                                                              + getRGB + arraycopy + setRGB（约 110ms）
                                                              + toComposeImageBitmap
```

也就是说，**真正该砍的是 WebP → PNG → ImageIO 这条往返**：Skiko 已经把 WebP 解成像素了，
却又编码成 12MB 的 PNG，交给 ImageIO 再解一次，然后才轮到我们搬像素。

**下一步（有数据支撑的做法）**：让 Skiko 解码后**直接读像素**（`Bitmap.readPixels`），
在 IntArray 上做反切片，再用 `Image.makeRaster` 建位图 —— 一次性省掉
PNG 编码（实测 206 ms 那一行就是它）、12MB 中间产物、ImageIO 二次解码、getRGB/setRGB 与
BufferedImage→Compose 的转换。风险是像素格式（ARGB 与 premultiplied RGBA 的差别）可能导致
颜色错乱，因此**必须保留现有的 ImageIO/PNG 兜底路径**，并先用一张图对比新旧两条路径的输出
（逐像素比对或至少尺寸与通道顺序检查），再交给用户看颜色。

## 大功能方案（1.9.014）：Skiko 直读像素，砍掉 WebP→PNG→ImageIO 往返

**API 已核实**（`javap` 读 skiko-awt-0.150.1，不是凭记忆）：

| 用途 | 方法 |
| --- | --- |
| 解码（含 WebP） | `Image.makeFromEncoded(byte[])` |
| 建目标位图 | `Bitmap().allocPixels(ImageInfo.makeN32Premul(w, h))` |
| Skia 图像 → 位图 | `Image.readPixels(Bitmap)`（另有带 srcX/srcY 的重载） |
| 位图 → 字节 | `Bitmap.readPixels(ImageInfo, srcX, srcY, rowBytes): byte[]` |
| 字节 → 位图 | `Bitmap.installPixels(ImageInfo, byte[], rowBytes)` |
| 位图 → Skia 图像 | `Image.makeFromBitmap(Bitmap)` / `Image.makeFromPixmap(Pixmap)` |
| 位图 → 像素视图 | `Bitmap.peekPixels(): Pixmap` |

**关键发现：反切片只是按 band 整行搬移，与通道顺序无关。**
我此前担心"ARGB 与 premultiplied RGBA 不一致会导致颜色错乱"，现在看这个担心被夸大了：
`System.arraycopy` 搬的是**整行**，同一行的字节一起移动，通道顺序是 RGB 还是 BGR 都不影响结果；
premultiplied 也只是数据本身的性质，不因搬行而改变。**真正要保证的只有两点**：
1. 读与写用**同一个 ImageInfo**（同一 alpha 类型与色彩空间）；
2. 行跨度（rowBytes）按 `info.minRowBytes` 对齐，不能假设等于 width*4。
这两点都是可核对的，不是碰运气。

**收益（按已有数据推算）**：省掉一次 PNG 编码（日志里那一行本身花 206 ms 且产出 12MB）、
一次 ImageIO 对 12MB PNG 的解码、`getRGB`/`setRGB`（本地基准共约 100 ms）
以及 BufferedImage→Compose 的转换；保留 `toComposeImageBitmap()` 这一步（它仍需要）。

**兜底**：新路径任何一步返回 null/false 或抛异常，就退回现有的 ImageIO → Skiko 转码 PNG 路径，
并在日志里写明走了哪条路（`反切片：直读路径` / `反切片：PNG 兜底路径`），
这样用户日志能直接看出两条路各用了多少次，不必靠猜。

**自验方式**（不需要界面）：写一个本地比对程序，对同一张 WebP 分别用两条路径解出像素数组，
逐行比较（band 搬移是确定的，两条路应当得到相同的行分布）；若一致再请用户看颜色。

## 反切片的新做法：用 Skia 自己画 band（本地实测有效，待接入）

三次"取像素"的尝试失败后换思路：**反切片的本质是把各 band 按新顺序画到画布上**，
不需要把像素取出来 —— 直接让 Skia 画。

```kotlin
val surf = Surface.makeRasterN32Premul(w, h)
val c = surf.canvas
for (b in ImageUnscramble.bands(w, h, sliceCount)) {
    c.drawImageRect(src,
        Rect.makeLTRB(0f, b.srcY.toFloat(), w.toFloat(), (b.srcY + b.height).toFloat()),
        Rect.makeLTRB(0f, b.dstY.toFloat(), w.toFloat(), (b.dstY + b.height).toFloat()))
}
val fixed = surf.makeImageSnapshot()      // 直接 toComposeImageBitmap()
```

**本地实测（合成图 2116x3037，与用户日志同尺寸）**：

| 阶段 | 新做法 | 现在的做法 |
| --- | --- | --- |
| 解码 WebP | 1.2 ms | 同 |
| 反切片 | **81.2 ms**（Skia 画 band） | 编码 PNG 666.7 ms + ImageIO 读 PNG 759.9 ms + getRGB 277.5 ms |
| 中间产物 | 无 | 12 到 25 MB 的 PNG 字节 |

即这一段的成本从约 **1700 ms 降到约 82 ms**，且不再有 12MB 中间产物。

**API 已核实**：`Surface.makeRasterN32Premul(w,h)`（在 Companion 上）、
`Surface.getCanvas()`、`Canvas.drawImageRect(Image, Rect, Rect)`、`Surface.makeImageSnapshot()`。
band 的计算直接复用共享层的 `ImageUnscramble.bands(w, h, count)`，**公式一字不改** ✓。

**一个必须修正的验证方法（本轮踩到）**：我最初拿"合成原图"逐像素严格比对，结论是"重排不符" ——
但中间经过了**有损的 WebP**，逐像素严格相等本来就不成立。正确做法是
**与解码后的源图比较**（两条路都从同一张解码图出发，才可能逐像素相等）；
或对源图与输出图各自取同一行做比较。下次验证按这个来。

**未做**：接入 Kotlin（`loadScrambled` 的新路径 + 保留 PNG 兜底）、以及用上面修正后的方法复验。

## 机器负载纪律（用户指出"让宿主机的 SoC 疯狂空转"之后定的）

用户反馈宿主机 SoC 空转。排查当时的状态：`800%idle`、无 java/gradle/qemu 进程，
但 **swap 已用 6.9GB**、且反复构建留下的 **Kotlin 编译守护进程会常驻**。
判断：不是单个失控进程，而是"我反复起重型构建 + 内存吃紧导致换页抖动"。

**从今往后的做法（写下来照着做）**：
1. 构建一律 `--no-daemon`（已经在用），**构建完成后主动 `pkill -f KotlinCompileDaemon`**
   —— 这个守护进程默认不退出，会一直占内存；
2. **不要连续起多个重型后台任务**（Gradle 构建、fatJar 打包、Java 基准）——
   一次只跑一个，跑完再起下一个；
3. 大件打包（尤其 46MB 的 Windows 单体 jar 与三次 zip）不要和构建同时进行；
4. 起后台任务前先看 `/proc/loadavg` 与 swap 使用量；吃紧就先等，不要叠加。

## 负载事故与新的构建纪律（用户："咋把api修炸了，看日志"）

**现象**：应用启动后报「主机发现全部失败」「API 主机尚未初始化」，用户以为接口被我改坏。

**排查结论**：不是代码问题。
- 发现地址从命令行直连 **HTTP 200、1.87 秒**（应用超时是连接 20 秒 / 读 30 秒，并不短）；
- 同时系统 **负载 20.3**、内存 15.1G 用了 12.4G、**swap 用了 6.9G**；
- 负载高但没有 CPU 大户 → 是 **swap 换页 I/O 阻塞**（进程卡在等内存），
  这种状态下应用连 20 秒的连接都撑不住，于是主机发现全部超时。

**成因（我的责任）**：反复起 Gradle 构建（每次一个 JVM + 一个常驻的 Kotlin 编译守护进程），
加上若干 Java 基准，把内存推到换页；我还一边让用户测试、一边在后台重编译。

**新纪律（写死，照做）**：
1. **用户在测试时不构建**；要构建先问，或等其离开；
2. 一轮**最多一次**构建，改动攒起来一次编；
3. 构建一律 **`nice -n 19`**，不与前台应用抢 CPU；
4. 构建结束**立刻** `pkill -f "[K]otlinCompileDaemon"`（方括号技巧，避免 pkill 匹配到自身）；
5. 不跑与当轮目标无关的基准；跑过的基准用完即删；
6. **构建前先看负载与 swap**：负载高于 ~6 就等，不要叠加。

**另记一条自杀事故**：`pkill -f "gradle"` 会匹配到**自己**的命令行（模式字面量出现在参数里），
结果把自己的构建任务也杀了（`[killed by signal: SIGTERM]`）。以后一律用 `[g]radle` 这种写法。
